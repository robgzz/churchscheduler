# V6.4.0 deployment: Azure and native iOS

1. **Before deployment:** export the current song library from Admin → Content → Songs → Export CSV / Excel; preserve a backup of production assignment/history data using your established Azure backup process. Source numbers replace legacy numbers on first server startup.
2. Extract the **full** V6.4 ZIP. Copy into the `churchscheduler` Git working tree, replacing the previous version; preserve `.git`. Remove old files from the old release so stale V7 tests do not remain mixed with V6.4. The V6.4 full ZIP is the deployable app package; do not deploy the infrastructure-only archive as the app.
3. Run `npm install --include=dev`, `npm test` and `npm run lint:syntax` locally, commit and push to your existing deployment branch. GitHub Actions will deploy to Azure Container Apps if your pipeline remains configured for that branch.
4. Watch Azure Container App startup and health. On the first boot, the `seed` migration scans existing songs and updates rows using the authoritative uploaded anthology, then records seed version 5. Verify Admin → Content → Songs shows **226 active songs**, including #68, #69–99, 203a/b and 223a/b. Other locally created old songs are retained but deactivated rather than deleted.
5. In a regular member account, open **Cantos / Songs** and test search by number and title and reading lyrics. In Admin → Content → Songs, open and edit a single song (without unintentionally overwriting its content). Confirm old/revised assigned songs on future programs before worship services.
6. Because the Capacitor `server.url` in this release points at your deployed Azure website, an already-installed native iOS shell may display updated web content after Azure deployment. For a **new App Store/TestFlight build**, use the V6.4 source on the Mac, `npm install --include=dev`, `npx cap sync ios`, and `npx cap open ios`. Preserve the APNs callbacks and push capability in the locally generated `ios/` project. Set version `6.4.0` and a **new, unused** build number in Xcode (for example, `3` if prior uploads used `1` and `2`). Choose a generic physical iOS device, Product → Archive → Organizer → Distribute App → Upload, then add the build to your internal TestFlight group.
7. On a physical iPhone: sign in with a normal member, validate the 226-title library and text, check programs remain collapsed, switch languages and themes, recheck parent notifications, and confirm account deletion with an expendable test account before submitting Apple review material. Never demonstrate deletion using your real administrator account.

Do not change everyone's passwords to `welcome`; it is only the initial password for newly provisioned accounts.

Note: The publisher is responsible for verifying permissions to distribute lyric content through App Store apps; converting user-supplied slides does not itself establish rights.
